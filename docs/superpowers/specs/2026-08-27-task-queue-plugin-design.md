# Custom Task Queue Plugin Design

## Summary

`custom:task-queue` is a native host plugin backed by the host's existing data-plane NATS connection. It provides a durable work queue with task state, cooperative cancellation, timeout callbacks, heartbeat callbacks, attempt-failure callbacks, and completion callbacks. It is not a general-purpose extension of `wasmcloud:messaging`; the latter uses core NATS and does not provide persistent work-queue semantics.

The first implementation is P3-only. It does not provide P2 bindings or named/labeled instances. A workload binds one queue through a required `config.queue` value; queue isolation is the routing boundary.

## Terms

- **Producer / submitter**: a component that imports `custom:task-queue/producer` and must export `custom:task-queue/observer`.
- **Consumer / worker**: a component that imports `custom:task-queue/task-control` and exports `custom:task-queue/worker`.
- **Queue**: a shared named resource configured as `config.queue`. It is not owned by a workload. Multiple producers and consumers may bind the same queue.
- **Task**: one immutable queue message with host-managed state. `task_id` is generated by the plugin and is opaque to business schemas.

## Architecture

```text
Producer wasm
  | submit(task)
  v
Task Queue Plugin (host-local)
  | JetStream publish
  v
<queue> WorkQueue stream
  |
  v
Shared durable pull consumer
  |
  v
Task Queue Plugin on one host
  | resolve queue, attempt, cancellation, heartbeat, retry
  v
Consumer wasm handle-task
  |
  +--> on-attempt-failed --> producer observer via core NATS callback
  +--> on-heartbeat      --> producer observer via core NATS callback
  +--> on-complete       --> producer observer via core NATS callback
```

The plugin is a host-level singleton. It maintains:

- per-queue JetStream contexts and runtime settings;
- per-component workload routing;
- per-running-task lease and cancellation state;
- host-local serialized callback workers.

## NATS Connection

The plugin must reuse the host's existing data-plane NATS client. It does not accept `nats-url` or `jetstream-domain` in workload config. TLS CA/cert/key remain host-level connection settings and are handled by `washlet::connect_nats`.

In dev mode, `dev.data_nats_url` must point to a JetStream-enabled NATS server. The plugin must fail at startup if no data NATS client is available; it must not silently fall back to in-memory mode.

The plugin creates a JetStream context from the shared client.

## WIT Model

Package version: `custom:task-queue@0.1.0`.

```wit
package custom:task-queue@0.1.0;

interface types {
    record task {
        payload: list<u8>,
    }

    variant task-status {
        succeeded,
        failed,
        dispatch-timeout,
        execution-timeout,
        cancelled,
        max-retries-exceeded,
    }

    record task-result {
        id: string,
        status: task-status,
        attempt: u32,
        output: option<list<u8>>,
        error: option<string>,
    }

    record task-info {
        id: string,
        status: task-status,
        attempt: option<u32>,
        created-at-ms: u64,
        dispatched-at-ms: option<u64>,
        completed-at-ms: option<u64>,
        cancel-requested: bool,
    }

    variant attempt-error-source {
        guest,
        system,
    }

    record attempt-failure {
        id: string,
        attempt: u32,
        source: attempt-error-source,
        error: string,
        started-at-ms: option<u64>,
        failed-at-ms: option<u64>,
        duration-ms: option<u64>,
    }
}

interface producer {
    use types.{task, task-info};

    submit: func(task: task) -> result<string, string>;
    query-status: func(task-id: string) -> result<option<task-info>, string>;
    cancel-task: func(task-id: string) -> result<_, string>;
}

interface task-control {
    send-heartbeat: func(task-id: string, info: string) -> result<_, string>;
    is-cancelled: func(task-id: string) -> bool;
}

interface observer {
    on-heartbeat: async func(task-id: string, info: string) -> result<_, string>;
    on-attempt-failed: async func(event: attempt-failure) -> result<_, string>;
    on-complete: async func(result: task-result) -> result<_, string>;
}

interface worker {
    handle-task: async func(task: task) -> result<option<list<u8>>, string>;
}

world task-producer {
    import custom:task-queue/producer;
    export custom:task-queue/observer;
}

world task-consumer {
    import custom:task-queue/task-control;
    export custom:task-queue/worker;
}
```

### Binding Rules

Role constraints are orthogonal. A component may be both producer and consumer.

| Import | Export | Result |
|---|---|---|
| `producer` | `observer` | Allowed |
| `task-control` | `worker` | Allowed |
| `producer` + `task-control` | `observer` + `worker` | Allowed |
| `producer` | missing `observer` | Rejected |
| `task-control` | missing `worker` | Rejected |
| exported `worker` | missing `task-control` | Rejected |

The plugin's `HostPlugin::world()` advertises:

- provided imports: `custom:task-queue/producer`, `custom:task-queue/task-control`;
- callable exports: `custom:task-queue/observer`, `custom:task-queue/worker`.

Only P3 async bindings are generated. There is no P2/P3 compatibility layer.

## Queue Naming and Sharing

`config.queue` is required and is never inferred from workload/component names.

Valid queue names must match:

```text
^[A-Za-z0-9_-]{1,64}$
```

The first character must be alphanumeric. Queue names must not contain `.`, `*`, `>`, `/`, whitespace, or other subject-delimiting characters.

A queue is a shared namespace. It has no owner. Multiple producers and multiple consumers may bind it. A queue's first bound workload creates the JetStream resources lazily. Later bindings must resolve to an identical configuration or binding fails.

If a workload uses both producer and consumer roles, all of its task-queue host-interface entries must specify the same `config.queue`.

## JetStream Objects

| Object | Name | Purpose | Retention |
|---|---|---|---|
| TASKS | `<queue>` | durable task queue | WorkQueue |
| RESULTS | `<queue>-results` | terminal result archive | Limits |
| META | `<queue>-meta` | status metadata and CAS state | KV bucket with TTL |

Resources are created with `get_or_create_stream` and `create_key_value`. Heartbeat does not use JetStream.

Subject layout:

```text
<queue>.tasks.<task-id>
<queue>.results.<task-id>
<queue>.heartbeat
<queue>.cb.<target-hash>.heartbeat
<queue>.cb.<target-hash>.attempt-failed
<queue>.cb.<target-hash>.complete
```

The TASKS consumer uses filter `<queue>.tasks.>`; each task is published to its own subject. This keeps per-task subjects easy to inspect and avoids introducing a separate workload/component routing key.

The callback target hash is deterministic:

```text
hash_input = "v1\0<queue>\0<namespace>\0<workload>\0<component>"
target_hash = base32(sha256(hash_input)[0..16])
```

Callback subjects use queue groups named `<queue>.cb.<target-hash>` so multiple replicas of the same submitter receive each callback only once.

## Configuration

Configuration is supplied through each relevant host-interface entry. Defaults are built into the plugin. All entries binding the same queue must produce the same resolved configuration; otherwise binding fails.

| Key | Type | Default | Meaning |
|---|---|---|---|
| `queue` | string | required | queue resource name |
| `ack-wait-ms` | u64 | `30000` | JetStream ack wait |
| `lease-renew-interval-ms` | u64 | `10000` | interval for `AckKind::Progress` |
| `default-dispatch-timeout-ms` | u64 | `600000` | 10 minutes from submit to first execution |
| `default-execution-timeout-ms` | u64 | `3600000` | 1 hour cooperative execution deadline |
| `max-deliver` | u64 | `3` | maximum JetStream deliveries per task |
| `retry-backoff-ms` | CSV u64 | `1000,5000,15000,60000` | JetStream consumer backoff |
| `disable-result-archive` | bool | `false` | do not create or use `<queue>-results` |
| `inline-payload-max-bytes` | u64 | `1048576` | maximum inline submit payload |
| `heartbeat-max-info-bytes` | u64 | `8192` | maximum heartbeat info bytes |
| `heartbeat-min-interval-ms` | u64 | `1000` | minimum interval between accepted heartbeats |
| `callback-workers` | u64 | `8` | host-local callback worker count |

Per-task configuration overrides are not supported. In particular, a task cannot override dispatch or execution timeouts.

## Task Schema

The JetStream envelope is internal and should include its own `schema_version`. The business payload is opaque to the plugin and has no plugin-managed schema or version. Business protocols are responsible for their own payload and output versioning.

P0 payload rules:

- type is inline `list<u8>`;
- size must be no greater than `inline-payload-max-bytes`;
- `submit()` fails if the limit is exceeded;
- no automatic object-store spill;
- callers should upload large objects to blobstore/object storage and pass references in the payload.

`task_id` is generated by the plugin using UUIDv7 or an equivalent monotonic unique ID. It is not user-specified. There is no idempotent-submit guarantee; callers receive the generated ID as the result of `submit()`.

## Task State Machine

Minimum states:

```text
Queued
Claimed
Running
AttemptFailed
Succeeded
Failed
DispatchTimeout
ExecutionTimeout
Cancelled
MaxRetriesExceeded
```

`AttemptFailed` is a non-terminal state. All other listed terminal states are final. `task_id` remains stable across redeliveries and retries.

Terminal statuses:

```text
succeeded
failed
dispatch-timeout
execution-timeout
cancelled
max-retries-exceeded
```

## Submission, Dispatch, and Retry

### Submission

`producer.submit(task)` performs:

1. validate payload and queue config;
2. generate `task_id`;
3. create META entry with `Queued`;
4. publish the JetStream TASKS message;
5. return `task_id`.

If META creation succeeds but TASKS publish fails, the implementation must handle the orphan META entry through normal scanner/recovery or explicitly remove it. This is an implementation test area.

### Dispatch Timeout

Dispatch timeout is actively detected; it does not rely solely on a worker pulling the message.

Each queue has a background scanner that checks META entries in `Queued` state whose dispatch deadline has passed.

Flow:

1. scanner finds an expired queued task;
2. CAS META `Queued -> DispatchTimeoutPending` using KV revision;
3. only the winner becomes the timeout owner;
4. owner removes the TASKS message from the WorkQueue;
5. writes terminal result to RESULTS and META;
6. publishes the terminal callback;
7. publishes `on-complete(dispatch-timeout)`.

The worker must CAS or verify META before executing. If it finds the task already terminal or timeout-owned, it acknowledges/terminates the stale TASKS message without executing or invoking callbacks.

The dispatch timeout terminal reason is represented in `on-complete(task-result.status = dispatch-timeout)`.

### Worker Pull and Lease Renewal

A shared durable pull consumer is used for all hosts binding the queue. WorkQueue semantics are preserved by acknowledging only after the attempt reaches its final disposition.

After pulling a task:

1. split out the JetStream `Acker`;
2. verify META is claimable;
3. start a lease renewer;
4. call guest `handle-task`.

The renewer calls:

```rust
acker.ack_with(async_nats::jetstream::AckKind::Progress)
```

every `lease-renew-interval-ms` (default 10 seconds). With default `ack-wait-ms = 30000`, there are normally two opportunities to recover from one failed renewal.

Terminal disposition is sent only after the lease renewer is cancelled and awaited:

| Outcome | Queue action |
|---|---|
| success | `Ack` |
| transient failure with retry remaining | `Nak(Some(delay))` |
| transient failure at max delivery | `Term`, then terminal result |
| fatal/system terminal failure | `Term`, then terminal result |
| cancellation before execution | `Term` or `Ack`, then terminal result |

The queue model is at-least-once execution. Guest business effects must be idempotent by `task_id`.

## Failure and Retry

`handle-task` uses the minimal signature:

```wit
handle-task: async func(task: task) -> result<option<list<u8>>, string>;
```

Rules:

- `Ok(Some(output))` succeeds with output;
- `Ok(None)` succeeds without output;
- `Err(error)` is a transient failure;
- wasm trap/runtime errors are also transient/system failures;
- every retryable failure emits `on-attempt-failed`;
- the final attempt that reaches the delivery limit does not emit `on-attempt-failed`; it emits `on-complete(max-retries-exceeded)`;
- JetStream's message `delivered` count is the sole attempt source. The plugin does not maintain a second retry counter;
- attempt numbering is 1-based.

`attempt-failure` contains:

- `id`;
- 1-based `attempt`;
- `source = guest` or `system`;
- error text;
- optional started/failed timestamps and duration.

The event does not include the task payload.

## Cooperative Timeout and Cancellation

Execution timeout and user cancellation are cooperative. The plugin does not force-interrupt Wasm execution.

### Execution Timeout

The queue-level default is one hour. There is no per-task override. A guest must poll:

```wit
task-control.is-cancelled(task-id)
```

to observe cancellation, and the implementation should use the same control path to expose the task's execution deadline. On deadline expiry, the guest is expected to clean up and return. In P0, the plugin does not force-interrupt a guest that never returns or never polls.

If the guest returns after the deadline:

1. mark `execution-timeout`;
2. write RESULTS/META;
3. invoke `on-complete(execution-timeout)`.

If the guest never returns, the task may remain running under P0's accepted limitation.

### User Cancellation

`producer.cancel-task(task-id)`:

- `Queued`: CAS `Queued -> Cancelling`, remove TASKS message, then terminal callback.
- `Running`: CAS/mark `cancel_requested = true`; guest sees it through `is-cancelled()` and returns.
- Terminal: idempotent no-op or a clear error.

Cancellation is advisory for a running task. If the guest completes before observing cancellation, the actual execution result wins. The result may retain `cancel_requested` metadata, but no late `cancelled` callback replaces a real final result.

If a redelivered task sees cancellation requested, it should not execute; it participates in producing the appropriate terminal result without duplicating callbacks.

## Heartbeats

Heartbeat direction is consumer to producer:

```wit
task-control.send-heartbeat(task-id, info)
```

The plugin forwards it through the submitter's callback subject and invokes the producer's:

```wit
observer.on-heartbeat(task-id, info)
```

Rules:

- `info` is UTF-8 text and must be at most `heartbeat-max-info-bytes` (default 8 KiB);
- calls closer together than `heartbeat-min-interval-ms` return an error;
- errors do not affect JetStream lease renewal, task execution, or terminal state;
- large artifacts must be stored in blobstore/object storage and referenced by key/URL;
- delivery is best-effort and may be lost during callback routing.

Heartbeat is unrelated to JetStream `AckKind::Progress`. Progress renewal proves queue-lease liveness; heartbeat is a business event to the producer.

## Callback Routing

Callbacks are published over core NATS. No callback JetStream stream is created.

Every callback event includes the submitter's namespace, workload, and component in its payload. The subject is derived from the deterministic submitter target hash.

All hosts running the plugin subscribe to callback subjects with a queue group keyed by that target hash. When a host receives a callback:

1. resolve the local producer workload/component route;
2. build a fresh store and bindgen proxy as needed;
3. invoke `on-heartbeat`, `on-attempt-failed`, or `on-complete` inside `store.run_concurrent(...)`;
4. log failures and metrics.

If no host currently has the submitter, the callback is dropped with logging. `on-complete` remains recoverable through `<queue>-results`.

Callbacks are serialized per `(queue, submitter target, task_id)` using host-local sharded callback workers. Different tasks may run in parallel. The default worker count is 8.

## Results Archive

Unless `disable-result-archive` is enabled, the plugin creates `<queue>-results` with `Limits` retention. It is the durable source of terminal results.

Result archive messages include:

```json
{
  "schema_version": 1,
  "task_id": "...",
  "status": "succeeded",
  "attempt": 3,
  "output": "...",
  "error": null,
  "queue": "agent-task",
  "submitter": {
    "namespace": "default",
    "workload": "http-api",
    "component": "http-api"
  },
  "created_at_ms": 123,
  "started_at_ms": 456,
  "completed_at_ms": 789,
  "duration_ms": 333,
  "host_id": null
}
```

`output` is capped by `inline-payload-max-bytes`. The guest `on-complete` callback may receive the full output, but the archive omits or truncates oversized output and marks that fact.

The result subject is `<queue>.results.<task-id>`.

## Workload Lifecycle

Queue data is independent of workload lifecycle.

- Submitter unbind/redeploy does not cancel queued or running tasks.
- Consumer component unbind cancels local execution and lease renewal, then `Nak(Some(short delay))` so another worker can take over.
- Callbacks may be published when the producer is temporarily absent; they are lost at the wasm callback layer but terminal state remains archived.
- Guests must be idempotent because JetStream redelivery and restarts can repeat effects.

## Observability and Testing Requirements

Metrics and logs should cover:

- submit/queued/claim/running/terminal transitions;
- dispatch latency;
- execution duration;
- retry and delivery attempt;
- dispatch/execution timeout;
- cancellation;
- lease renewal failures;
- callback publish failures;
- callback invoke failures;
- poison messages;
- queue depth and consumer lag.

Tests must include:

1. pure state-machine unit tests;
2. fake guest tests for immediate success, empty success, transient failure, final retry exhaustion, and runtime trap;
3. JetStream integration tests for ack/nak/term/redelivery/backoff;
4. multiple-host competition and lease-expiry tests;
5. dispatch timeout ownership and CAS conflict tests;
6. queued and running cancellation tests;
7. heartbeat size/rate errors;
8. payload limit tests;
9. callback target hash and queue-group dedup tests;
10. submitter/worker unbind and redeploy tests.

## Deliberately Excluded from P0

- named/labeled instances;
- P2 bindings;
- user-specified or idempotent task IDs;
- per-task timeout overrides;
- automatic object-store payload spill;
- forced Wasm interruption / epoch interruption;
- hard cancellation;
- result wait/get-result;
- generic task metadata/tags;
- broadcast result callbacks;
- queue ownership or authorization;
- callback JetStream persistence.
